TP3 : Du commit au cluster

Durée estimée : ~1h30

Point de départ : ArgoCD déploie api-dev et api-prod depuis ton dépôt (TP2), avec une image api:initial chargée à la main dans le cluster.

Objectif : un commit dans app/ arrive en dev sans aucune intervention. Le pipeline construit l'image et écrit son tag dans git. ArgoCD fait le reste.

Le pipeline complet est dans les slides « Le pipeline complet ». Ne le recopie pas sans le lire : tu dois savoir dire à quoi sert chaque étape.

1. Écris le pipeline

Dans .github/workflows/pipeline.yml. Il se déclenche uniquement sur un push sur main qui modifie app/, et il fait trois choses :

  1. construire l'image à partir de app/, avec pour tag les 8 premiers caractères du commit ;
  2. la pousser dans la registry de GitHub, sous le nom ghcr.io/<compte>/<depot> en minuscules ;
  3. écrire ce tag dans deploy/overlays/dev/kustomization.yaml avec kustomize edit set image, puis commiter et pousser, avec l'auteur pipeline-ci.

Deux permissions sont nécessaires, à déclarer dans le fichier : contents: write (pousser un commit) et packages: write (pousser une image). Aucun secret à créer : GitHub fournit un token à chaque exécution.

2. Premier passage

Modifie quelque chose de visible dans app/app.py (par exemple la valeur de service), commite, pousse, et suis le pipeline dans l'onglet Actions de ton dépôt.

Quand il est vert :

git pull
git log -3 --format='%an | %s'
cat deploy/overlays/dev/kustomization.yaml

Tu dois voir un commit de pipeline-ci, et un newTag qui n'est plus initial.

3. Rends l'image accessible

Ton cluster doit pouvoir télécharger l'image sans s'authentifier.

Sur la page de ton dépôt, colonne de droite, Packages : ouvre le package, puis Package settings, et tout en bas Change visibility, Public.

4. Regarde le déploiement se faire

kubectl --context kind-plateforme -n argocd get applications --watch
kubectl --context kind-plateforme -n dev get deploy api \
  -o jsonpath='{.spec.template.spec.containers[0].image}' ; echo

L'image de dev doit porter le tag écrit par le pipeline. Vérifie que la modification est bien en ligne :

kubectl --context kind-plateforme -n dev port-forward svc/api 8080:80
curl localhost:8080/

5. Promeus en prod

prod tourne toujours sur api:initial. La promotion est un commit : recopie dans deploy/overlays/prod/kustomization.yaml le newName et le newTag de dev, commite, pousse.

C'est volontairement manuel : en dev tout part automatiquement, en prod quelqu'un décide.

6. Vérifie que la boucle est fermée

Regarde l'historique des pipelines : le commit de pipeline-ci n'a pas déclenché un second pipeline. Sais-tu dire pourquoi ?

Pièges connus

  • ImagePullBackOff en dev après le pipeline : le package est privé (étape 3), ou le nom de l'image contient des majuscules (un nom d'image est toujours en minuscules).
  • Le pipeline échoue au git push : il n'a pas le droit d'écrire dans le dépôt (permission contents: write, étape 1).
  • nothing to commit : le pipeline a été relancé sur un commit déjà déployé, le tag est déjà le bon.
  • Ton git push est refusé après un passage du pipeline : il a poussé un commit entre-temps. Fais git pull --rebase puis repousse. Prends l'habitude de faire un pull avant de travailler.
  • Le pipeline ne se déclenche pas : ton commit ne touche pas app/.

✅ Validation : tu modifies app/app.py, tu pousses, et quelques minutes plus tard la nouvelle version répond en dev, sans que tu aies tapé un seul kubectl pour la déployer.
