TP4 : Un secret dans git

Durée estimée : ~30′

Point de départ : le pipeline déploie en dev (TP3). L'API répond "jeton_present": false : elle attend une variable d'environnement JETON que personne ne lui donne.

Objectif : lui fournir ce secret par git, sans jamais le commiter en clair.

Les exemples complets sont dans les slides « Des secrets dans git ».

1. Installe le contrôleur, par ArgoCD

Ajoute un fichier deploy/argocd/sealed-secrets.yaml : une Application nommée sealed-secrets, dont la source n'est pas ton dépôt mais un chart Helm :

Champ Valeur
source.repoURL https://bitnami.github.io/sealed-secrets
source.chart sealed-secrets
source.targetRevision 2.20.0
source.helm.values fullnameOverride: sealed-secrets-controller
destination.namespace kube-system
syncPolicy automated avec prune: true et selfHeal: true, comme pour tes autres applications

Commite, pousse, et attends que l'application soit Synced et Healthy. Tu n'as lancé aucun helm install : tu as ajouté un fichier dans git.

2. Installe le client kubeseal

Télécharge la version 0.40.0 pour ton système sur https://github.com/bitnami/sealed-secrets/releases (ou brew install kubeseal sur macOS), puis vérifie :

kubeseal --version

3. Scelle un secret

kubectl create secret generic api-secret --namespace dev \
    --from-literal=JETON=une-valeur-que-tu-choisis \
    --dry-run=client -o yaml \
  | kubeseal --context kind-plateforme --format yaml \
  > deploy/overlays/dev/api-secret-scelle.yaml

Ouvre le fichier produit : c'est un SealedSecret, et ta valeur n'y apparaît pas.

4. Branche-le

  1. Ajoute le fichier scellé aux resources de l'overlay dev (api-secret-scelle.yaml, juste sous ../../base).
  2. Dans deploy/base/deployment.yaml, fais lire le secret au conteneur avec envFrom et un secretRef vers api-secret, marqué optional: true (en prod, ce secret n'existe pas encore).
  3. Commite, pousse, attends la synchronisation.
kubectl --context kind-plateforme -n dev get sealedsecret,secret
kubectl --context kind-plateforme -n dev port-forward svc/api 8080:80
curl localhost:8080/                       # "jeton_present": true

Pièges connus

  • cannot fetch certificate : le contrôleur n'est pas encore démarré, ou il ne s'appelle pas sealed-secrets-controller dans kube-system (c'est le rôle de fullnameOverride).
  • jeton_present reste false : le pod n'a pas redémarré. Une variable d'environnement n'est lue qu'au démarrage : kubectl -n dev rollout restart deployment api.
  • file is not in or below au kubectl kustomize : Kustomize refuse de lire un fichier situé hors du dossier de l'overlay. Le fichier scellé doit être dans deploy/overlays/dev/.
  • Le secret n'est jamais créé : tu l'as scellé pour un autre namespace que dev.
  • Après un terraform destroy puis apply, le secret ne se déchiffre plus : le nouveau contrôleur a une nouvelle clé. Rescelle le secret (étape 3) et commite.
  • Tu as commité le Secret en clair par erreur : le supprimer dans un nouveau commit ne suffit pas, il reste dans l'historique. Ici, change simplement la valeur. En entreprise, on révoque le secret.

✅ Validation : l'API répond "jeton_present": true, et ta valeur est introuvable dans le dépôt.

git grep "une-valeur-que-tu-choisis"       # aucune ligne
